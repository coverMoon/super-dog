# 2026-06-28 blackW 实机越障复盘记录

## 1. Jun27_17-07-17_ 与 Jun27_17-09-43_ sim2real 观察

实机测试与 sim2sim 基本一致。`Jun27_17-07-17_` 上楼梯仍会在中段卡住，典型场景是前轮和后轮同时抵着台阶，随后可能出现轮子不转或持续空转。`Jun27_17-09-43_` 相对更容易抬腿，高墙前腿抬得更高，但楼梯卡住没有完全消失，高墙后腿有时仍会卡住。

当前判断：这不是单纯 sim2sim 可视化误差，而是策略学到的接触处理模式本身存在缺口。`17-07-17` 的 `stairs_continuous_scale = 1.6` 没有解决问题，说明楼梯中段不是只靠更强 anti-spin 就能处理；现象同时包含“不转”和“空转”，前者更像姿态/动作空间或接触几何卡死，后者才对应空转惩罚不足。继续简单加大 spin 惩罚可能压低轮子输出，使“不转”更明显。

`17-09-43` 证明更高的 `clearance_margin` 和 `over_lift_margin` 能释放抬腿高度，尤其改善高墙前腿动作；但后腿卡住说明剩余瓶颈不只是目标高度，而是最后一条腿越过障碍时缺少持续推进/滚过障碍的引导。当前 `wheel_obstacle_lift` 主要奖励触障后短窗口内抬到目标高度，`wheel_obstacle_spin` 主要惩罚接触且前进不足时的空转；两者都没有明确奖励“轮子已经接触/抬起后继续向前越过障碍”的过程。

后续优先方向应从“继续提高全局抬腿高度”转向更局部的接触后进度设计：楼梯侧重点是前后轮同时抵台阶时的重新推进和脱困，高墙侧重点是后腿/最后一轮的持续前向滚过。下一步仍建议保持改动小，优先做一到两个单变量实验，而不是同时加大 lift、spin 和稳定性约束。

## 3. Jun28_00-27-00_ 与 Jun28_00-27-53_ sim2sim 观察

两组都从 `Jun27_17-09-43_` 继续训练到 35000 iter，核心差异是 `wheel_obstacle_lift.high_obstacle_extra_active_time`：`Jun28_00-27-00_` 的实际 config 为 1.2，`Jun28_00-27-53_` 的实际 config 为 1.5。虽然两组保存的 `git_diff.patch` 都显示源码已改到 1.5，但判断实验参数应以各自 `config.json` 为准，因此本次先按 1.2 vs 1.5 对照分析。

sim2sim 观察显示，两组相对 `Jun27_17-09-43_` 对上楼梯都有改进，说明在当前 `clearance_margin = 0.06`、`over_lift_margin = 0.04`、`wheel_obstacle_unloaded_lift = -0.06` 的主线基础上，继续训练本身对楼梯中段接触节奏有帮助，并不一定需要立刻新增复杂 reward。

高墙表现上，`Jun28_00-27-00_` 反而更丝滑；`Jun28_00-27-53_` 偶尔出现动作变形，并重新出现前腿和后腿同时抬起的情况。当前判断是把高墙额外 active window 从 1.2 加到 1.5 后，确实延长了触障后抬轮/维持动作的作用时间，但窗口过长可能让策略在身体已经开始翻越后仍持续追求抬轮形态，导致前后腿时序边界变模糊，进而出现前后腿同时抬起或姿态变形。也就是说，1.5 对“保持高墙动作”有帮助，但可能开始侵占落地恢复和后续推进阶段。

现阶段不急着根据 sim2sim 单独改配置。优先等待 sim2real 结果：如果实机也确认 `Jun28_00-27-00_` 高墙更顺且楼梯已有改善，则后续高墙 active time 不宜继续加长，保留 1.2 或在 1.2 附近微调更稳；如果 `Jun28_00-27-53_` 在实机上楼梯明显更可靠但高墙动作变形可接受，再考虑是否为楼梯/高墙分 terrain type 做更局部的 active time 或恢复阶段约束。观察重点为高墙后腿越过时是否卡住、前后腿是否同时抬起、落地后姿态恢复，以及楼梯中段是否还出现前后轮同时抵台阶后的不转/空转。

## 4. Jun28_00-27-00_ 与 Jun28_00-27-53_ sim2real 结果

sim2real 结果与 sim2sim 观察基本一致，当前更倾向 `Jun28_00-27-00_`。该模型无论上楼梯还是翻越高墙都更好一些，高墙动作更连续、整体姿态更可控，也没有明显暴露 `Jun28_00-27-53_` 那种动作变形问题。

`Jun28_00-27-53_` 的高墙能力较差：一方面动作幅度偏大，实机上有伤关节的风险；另一方面仍可能在高墙处被卡住。结合其实际配置 `high_obstacle_extra_active_time = 1.5`，当前判断是额外 active window 过长后，策略会把触障后的抬轮/维持动作延续到翻越和恢复阶段，导致动作幅度变大、前后腿时序更容易混乱，反而削弱高墙翻越的稳定性。此前 sim2sim 中出现的前腿和后腿同时抬起，也可以作为该副作用的早期表现。

当前建议把 `Jun28_00-27-00_` 作为下一轮 obstacle 候选模型，而不是继续沿 `Jun28_00-27-53_` 加长 active time。后续若继续调高墙，不宜把 `high_obstacle_extra_active_time` 继续加到 1.5 以上；更稳妥的方向是保留 1.2，或在 1.2 附近做小步微调，同时观察楼梯中段卡住、高墙后腿越过、落地恢复和实机关节冲击。`Jun28_00-27-53_` 可以作为“active window 过长导致动作放大”的反例记录，不建议作为 sim2real 主线。
