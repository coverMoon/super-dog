## 2. Jun28_22-12-48_ 与 Jun28_22-14-55_ sim2sim 观察

sim2sim 观察显示，两组上楼梯相对之前都有一些改进，尤其是四个轮子同时碰到障碍时基本不会再卡住。这说明 `wheel_obstacle_lift` 的多轮协调聚合方向是有效的：四轮同时 active 时改用对角组合 reward，确实减少了所有轮子一起拿满 lift 奖励导致的同步卡死模式。

当前剩余问题更集中在后轮 pair：两个后轮同时碰到障碍后仍可能卡住，尤其在过高墙时更明显。这个现象和当前聚合逻辑也能对应上：四轮同时 active 时有对角 reduction，但只有后轮 pair 同时 active 时，目前只是 `max(rear) + residual * min(rear)`，并没有进一步要求后轮之间形成明确先后顺序，也没有奖励后轮接触后继续前向滚过障碍。因此策略可能已经避免了四轮同步卡死，但在高墙最后阶段，两个后轮同时抵住墙沿时仍缺少足够清晰的脱困信号。

暂不根据 sim2sim 继续改参数，先等待 sim2real 结果。实机观察重点：两组是否都减少四轮同时卡住；高墙后轮 pair 同时触障是否仍会卡住；B 组更强 residual 是否比温和组更能分开后轮动作，还是会削弱后轮抬腿/翻墙能力。如果实机也确认后轮 pair 是主要瓶颈，后续方向应优先考虑后轮 pair 的更强时序约束或后轮越障进度奖励，而不是再全局加大 lift height、spin 或 high-wall active time。

## 3. Jun28_22-12-48_ 与 Jun28_22-14-55_ sim2real 结果

sim2real 上楼梯结果与 sim2sim 基本一致：两组相比旧模型确实有好转，四轮同时触障卡死的问题减少，但仍会出现后轮卡住。两组中 `Jun28_22-12-48_` 的整体效果更好一些，说明温和 residual（楼梯 0.2、高墙 0.4）比 B 组强 residual 更适合当前策略；B 组虽然训练指标更干净，但实机行为不占优。

两个模型暴露出共同副作用：上楼梯时抬腿偏高，落地像砸向地面；同时两组都完全过不了高墙，甚至前轮也过不去。当前判断是多轮协调聚合虽然改善了四轮同步卡死，但默认同时作用在楼梯 type 3 和高墙 type 9 后，明显破坏了高墙所需的连续前轮抬起/翻越动作。高墙需要前轮有足够连续、强烈的 lift 信号去越过墙沿，而当前 pair/diagonal reduction 降低了多轮同时 active 时的总 lift credit，可能让前轮在触墙时拿不到足够收益，导致高墙能力直接丢失。

楼梯抬得过高则说明仅减少多轮同步奖励还不够，策略可能通过更高幅度的单轮/交替抬腿来弥补被削弱的 pair reward；加上当前楼梯 simple lift 不惩罚 over-lift，落地冲击会被放大。后续不应继续沿 B 组更强 residual 方向推进，也不应把多轮协调继续默认作用于高墙。

下一步建议：先将多轮协调限制到楼梯 type 3，关闭高墙 type 9 上的 coordination，恢复高墙原有 lift 聚合；同时优先以 `Jun28_22-12-48_` 的温和 residual 为基础，而不是 B 组。若继续优化楼梯落地冲击，可考虑恢复楼梯上的轻量 over-lift/落地冲击约束，或提高楼梯 residual，而不是继续压低 residual。高墙方向应单独处理后轮 pair 卡住问题，不能用同一套全局 pair/diagonal reduction 直接作用于高墙前轮翻越阶段。

## 6. 多轮协调组 sim2real 复盘与楼梯/高墙分离训练决策

后续 sim2real 观察确认，当前多轮协调相关模型的上楼梯能力仍不可靠：即使 sim2sim 中 `Jun29_00-58-26_` 看起来楼梯有所改善，实机仍会在四轮同时触障时卡住。高墙能力也没有恢复，两个模型在实机上仍基本过不了高墙。说明当前把楼梯和高墙混在同一套 obstacle 主线里继续微调，已经很难同时满足两类动作需求。

当前决定将楼梯和高墙分离训练：训练楼梯专线时直接取消高墙地形；训练高墙专线时也应取消楼梯相关地形或至少大幅降低其占比。这样可以避免楼梯需要的贴障滚动/低幅脱困动作与高墙需要的前轮强抬、后轮翻越动作互相牵制，也便于分别设计 reward 和观察指标。

需要保留一个重要观察：虽然 `Jun29_01-09-49_` 后期训练指标明显崩坏，不适合作为最终模型，但在不卡住的片段里，它的楼梯动作更接近期望状态：抬腿不高，更像轮胎贴着障碍滚过去。该现象很可能与 `stairs_use_simple_lift = False`、更强 over-lift 惩罚（`over_lift_margin = 0.02`、`over_lift_penalty_weight = 0.2`）有关。这提示楼梯专线不应继续追求更高 lift height，而应转向“轮胎贴着台阶沿滚过去”的低幅滚越模式。

下一轮楼梯专线建议从更干净且未崩坏的模型分叉，不直接继续 `Jun29_01-09-49_` 后期模型。可以把 `Jun29_01-09-49_` 中较好的行为假设拆出来做小步实验：取消高墙地形；保留或重新测试 `stairs_use_simple_lift = False`；使用轻量 over-lift 约束控制抬腿高度；暂时不要再叠加强 high-wall 参数。观察重点从传统 `rew_wheel_obstacle_lift` 大小转向实机/仿真行为：四轮同时抵台阶时是否能继续滚动、是否减少砸地、是否仍保持足够前向进度。

## 8. 楼梯专线 B 组配置：pair escape 强化

在楼梯专线 A 组基础上切到 B 组，保留取消高墙、`stairs_multi_contact_progress` 和 type 3 多轮协调，新增 `stairs_pair_escape` reward，scale 为 0.5。该项只在上楼梯、前进指令、同一 pair 的两个轮子同时触到前方障碍且 lift timer active 时生效，奖励 pair 内 lift progress 更好的那个轮子；前轮 pair 权重为 0.6，后轮 pair 权重为 1.0。

## 11. Jun29_12-05-58_ 与 Jun29_12-12-31_ sim2real 结果与下一组 AB 方案

sim2real 上楼梯暴露出新的主要问题：两组在实机上腿都抬得不够高，可能与齿轮虚位、传动间隙以及策略自身学到的低幅滚越有关。`Jun29_12-12-31_` 的 B 组相对表现好一点，说明 `stairs_pair_escape` 对实机脱困可能有正向作用，但当前 lift 高度余量不足，导致楼梯沿实际过不去或容易卡住。

当前配置为了抑制此前“抬太高、砸地”的问题，同时使用了 `stairs_use_simple_lift = False`、`clearance_margin = 0.05`、`over_lift_margin = 0.02`、`over_lift_penalty_weight = 0.2`。这套组合在 sim2sim 中会鼓励低幅贴障滚过，但在 sim2real 中可能过于贴边：仿真里刚好够的轮心高度，到了实机被齿轮虚位和关节响应误差吃掉后，就表现为抬腿不够。

下一组 AB 不建议再改 pair escape 或多轮触障逻辑，先固定 B 组结构，把变量集中在 lift 高度余量上。建议都从 `Jun29_12-12-31_` 继续训练，这样保留当前实机更好的 pair escape 行为，减少重新学习成本。

A 组：只放松 over-lift 约束，保持 `clearance_margin = 0.05`，将 `over_lift_margin` 从 0.02 调回 0.03，`over_lift_penalty_weight` 从 0.2 降到 0.1。目标是验证“不是目标高度不够，而是 over-lift 压得太紧，导致策略不敢留实机余量”。如果 A 组实机抬腿明显更足且没有恢复砸地，说明主要问题是 over-lift 约束太保守。

B 组：在 A 组基础上小幅提高目标余量，将 `clearance_margin` 从 0.05 提到 0.06，保持 `over_lift_margin = 0.03`、`over_lift_penalty_weight = 0.1`。目标是验证“即使放松 over-lift，目标高度仍不足，需要显式提高楼梯 lift target”。不建议一上来提到 0.065 或 0.07，否则容易回到此前抬腿偏高、落地砸地的问题。

观察重点：sim2sim 中两组都可能还能过楼梯，真正差异要看 sim2real。A/B 都要看前后腿实际越过台阶沿时是否还有余量、是否减少轮子顶住空转、是否重新出现抬腿过高和砸地。若 A 已经解决实机抬腿不足，优先选 A；若 A 仍偏低而 B 好，说明需要提高 `clearance_margin`；若 B 明显砸地或关节限位变重，则回到 A 或折中 `clearance_margin = 0.055`。

## 13. Jun29_18-03-27_ 与 Jun29_18-04-29_ sim2sim/sim2real 结果

两组 sim2sim 上楼梯都很顺利，说明当前补高度余量后，仿真内的楼梯通过能力已经不是主要瓶颈。`clearance_margin = 0.06/0.07` 与更宽的 over-lift 容忍都能在仿真中给足过台阶余量。

但 sim2real 仍出现和之前类似的问题：直线上楼梯不够稳，需要走 S 形才能比较稳定地通过。这个现象说明当前问题不再只是“抬腿高度不够”。S 形会让机身带入 yaw/lateral motion，使左右轮不再完全同时抵住同一条台阶沿，也会让前后轮触障相位产生错开；这等价于人为制造了接触时序差和横向逃逸空间。直线指令下，策略仍容易进入两轮或四轮同时顶住台阶沿的实机接触状态，而这种状态在 sim2sim 里没有充分暴露或没有足够代价。

结合代码看，当前训练已有困难地形的 y/yaw command sampling（楼梯属于 difficult terrain），但部署直线指令时 `tracking_lin_vel_y` 和 `tracking_ang_vel` 会约束策略保持直行。因此如果操作者给 S 形命令，策略能利用横摆脱困；但如果命令是直线，策略没有被明确鼓励在多轮触障时主动产生轻微错峰/横摆动作。继续单纯提高 `clearance_margin` 可能只会增加抬腿、冲击和关节限位风险，未必解决直线同时触障卡住。

下一步建议把问题拆成两条线做 AB。A 组走“命令暴露”方向：保留当前较稳的高度配置，强化楼梯上的 y/yaw command sampling，让策略更熟悉小幅 S 形上楼梯，目标是提高人工 S 形操控时的稳定性。B 组走“直线自脱困”方向：在楼梯多轮触障、前进进度不足时，加入局部错峰/横摆脱困奖励或放松障碍段 yaw/yaw tracking，让直线命令下也允许策略短时间产生小幅 yaw/lateral 来打破同时触障。B 组风险更高，需要严格限制只在楼梯、多轮触障、低进度时生效，避免学成平时蛇形走路。

当前不建议再继续单独增大 lift target。若要保留一个高度基线，优先选折中或偏稳配置，例如 `clearance_margin = 0.06~0.065`、`over_lift_margin = 0.03~0.035`、`over_lift_penalty_weight = 0.15`。后续观察重点应转为：直线命令下两前轮/两后轮是否同时顶住，策略是否能自己打破同步；S 形命令下是否更稳定；以及是否出现平地或普通楼梯段不必要的蛇形、姿态扰动和关节限位变重。

## 14. 后腿交替抬腿高度不足的修正观察

对 `Jun29_18-03-27_` 与 `Jun29_18-04-29_` 的 sim2real 现象进一步修正：实机并不是后腿同时抵住后完全不会打破同步，而是两个后腿会交替抬腿；主要问题是交替抬腿的高度偏低，导致后轮仍容易顶住台阶沿，需要通过 S 形路径提高通过稳定性。

这个观察把问题从“策略不会错峰/横摆脱困”收窄为“后腿 pair 已有时序，但后腿 lift 幅度或实机余量不足”。此前 `stairs_pair_escape` 对 B 组有一定帮助，说明 pair 内至少一个轮子先脱困的信号方向是对的；但当前 pair escape 只奖励 lift progress，并没有区分前腿/后腿的目标高度，也没有给后腿额外高度余量。继续全局提高 `clearance_margin` 会同时抬高前腿和后腿，容易带来前腿抬太高、砸地、姿态扰动和关节限位问题。

下一步更合理的 AB 应优先针对后腿，而不是继续全局加高度。A 组可以保持当前全局高度基线，例如 `clearance_margin = 0.06~0.065`、`over_lift_margin = 0.03~0.035`、`over_lift_penalty_weight = 0.15`，并在 `stairs_pair_escape` 中提高后腿 pair 的有效奖励或权重，例如只提高 `rear_pair_weight`，验证更强后腿脱困信号是否能让后腿抬得更充分。B 组可以增加一个只作用于楼梯后腿触障 active 阶段的 rear-lift height bonus/target offset，让后腿目标高度比前腿多一点实机余量，例如后腿额外 `0.01~0.015m`，同时保持前腿目标不变，避免全局抬高带来的砸地风险。

观察重点应从“四轮是否同时卡住”调整为：后腿交替抬腿时轮心是否真正越过台阶沿；后腿抬腿是否仍低于实机所需高度；前腿是否被无谓抬高；以及后腿加强后是否引入关节限位、落地冲击或机身俯仰扰动。若只提高 rear pair 奖励就能解决，优先保留奖励层改动；若奖励提高后仍抬不高，则说明需要显式增加后腿 lift target 或实机侧虚位补偿。

根据后腿实机观察，先切到后腿强化 A 组。当前不新增后腿 target offset，只强化已有 `stairs_pair_escape` 的后腿 pair 奖励，验证“后腿已有交替抬腿时序，但奖励不够强，导致抬得不够充分”这一假设。

## 16. 后腿强化 B 组配置
