## 1. Jun29_21-55-59_ 与 Jun29_22-00-35_ 训练结果初查

两组都是从 `Jun29_18-04-29_` 继续训练 1000 iter 到 36000，仍是楼梯专线：高墙地形比例为 0，上楼梯 type 3 比例为 0.6；保留 `stairs_multi_contact_progress = 1.0`、`stairs_pair_escape = 0.5`、`action_rate = -0.067`、`entropy_coef = 0.0032`。两组共同使用折中高度基线：`clearance_margin = 0.065`、`over_lift_margin = 0.035`、`over_lift_penalty_weight = 0.15`。

`Jun29_21-55-59_` 是后腿强化 A 组：不加后腿 target offset，只将 `stairs_pair_escape.rear_pair_weight` 提到 1.5，前腿权重仍为 0.6。`Jun29_22-00-35_` 是后腿 target offset 组，但实际配置比预期更激进：`rear_lift_target_offset = 0.03`，`rear_lift_target_offset_terrain_types = [3, 9]`，同时 `multi_wheel_coordination_terrain_types` 也变为 `[3, 9]`。由于当前高墙地形比例为 0，type 9 对这次训练标量基本不生效；但 `0.03m` 后腿 offset 明显大于原计划的 `0.01~0.015m`，需要按激进 B 组看待。

相对父模型 `Jun29_18-04-29_`，A 组末 100 `terrain_level` 从约 5.48 提到约 5.54，`rew_stairs_pair_escape` 从约 0.00247 提到约 0.00323，说明提高后腿 pair 权重确实让 pair escape 信号更强。A 组的 `dof_pos_limits`、`foot_impact_vel`、`orientation`、`torques` 都比父模型更轻，训练稳定性尚可；但 `rew_progress` 略低，`wheel_obstacle_spin` 更重一些，说明它更像是安全地强化后腿动作，而不是明显提高前进效率。

当前建议：两组都可以先做 sim2sim，但优先级应是 A 组 `Jun29_21-55-59_`。A 组变量更干净，风险较低，能直接验证“只加强后腿 pair 奖励是否足够”。B 组 `Jun29_22-00-35_` 可以作为激进后腿 offset 参考，重点看后腿是否明显抬高、是否砸地或扰动机身；如果 B 组 sim2sim 有明显大幅后腿动作或落地冲击，不建议进 sim2real。若 A 组后腿仍抬不够而 B 组确实改善，可以下一轮做温和 B：`rear_lift_target_offset = 0.01~0.015` 且只对 `[3]` 生效，不建议继续使用 0.03。

## 2. Jun29_21-55-59_ 与 Jun29_22-00-35_ sim2real 结果与下一步方向

sim2real 后确认，后腿强化 A 组和 B 组都仍会出现后腿卡住，没有肉眼可见的改善。A 组只提高 `rear_pair_weight`，B 组实际使用较激进的 `rear_lift_target_offset = 0.03`，但两者都未明显解决后腿过台阶沿时抬得偏低的问题。说明当前问题不只是后腿 target 高度数值不够，也可能是后腿到达更高 target 的 reward 驱动力不够强，或从 `Jun29_18-04-29_` 短续训 1000 iter 难以跳出原有低幅后腿策略。

需要注意，当前 `wheel_obstacle_lift` 中 `progress_weight = 0.7`，也就是 lift reward 主要奖励相对进度，真正贴近 target 的 `target_reward` 只占 0.3。`rear_lift_target_offset` 把后腿目标抬高后，如果策略只抬到一半，仍能拿到不少 progress reward；而 `stairs_pair_escape` 也主要奖励 lift progress。因此单纯把后腿 target 再抬高，可能只会让 reward 标量变难、训练更抖，但不一定让实机后腿真正抬到足够高。

下一轮可以稍微激进一些，但建议把激进性放在“后腿到达目标高度的奖励强度”上，而不是只继续加 target offset。一个较稳的 A 组可以不新增代码，只提高现有 reward 权重：从 `Jun29_21-55-59_` 或 `Jun29_18-04-29_` 分叉，设置 `stairs_pair_escape = 0.8~1.0`、`rear_pair_weight = 2.0~2.5`，并将 `progress_weight` 从 0.7 降到 0.55~0.6，让 target tracking 占比提高；高度保持 `clearance_margin = 0.065~0.07`、`over_lift_margin = 0.035~0.04`、`over_lift_penalty_weight = 0.12~0.15`。

更直接的 B 组建议新增一个只作用于楼梯后腿 active 阶段的 rear target tracking bonus，而不是继续复用全局 lift reward。该 bonus 可以只在 RL/RR 触障且 lift timer active 时，奖励后腿接近 target 或超过某个 lift progress 阈值，例如只奖励 `lift_progress > 0.75` 的部分。这样能明确鼓励后腿真正抬到高位，而不是只抬一点就拿到 progress。B 组风险是后腿动作幅度和关节限位变重，需要保持短训并重点看 sim2sim 后腿落地冲击。

如果先不改代码，建议下一组参数用 A 组强 reward 版本；如果允许新增 reward，建议做 B 组 rear target bonus。不要直接把 `rear_lift_target_offset` 提到 0.04~0.05 作为唯一改动，因为 0.03 已经没有肉眼改善，继续提高很可能只增加砸地、姿态扰动和 value loss 尖峰。

## 3. 强后腿 reward A 组配置

根据 `Jun29_21-55-59_` 和 `Jun29_22-00-35_` 的 sim2real 结果，切到下一轮 A 组：不新增 rear target bonus，只加强现有后腿 lift reward 的驱动力。该组从更干净的 `Jun29_21-55-59_` 继续训练，计划 1500 iter。

关键配置：`stairs_pair_escape` scale 从 0.5 提高到 1.0；`stairs_pair_escape.rear_pair_weight` 从 1.5 提高到 2.5，前腿权重保持 0.6；`wheel_obstacle_lift.progress_weight` 从 0.7 降到 0.55，让 target tracking 占比从 0.3 提高到 0.45；`rear_lift_target_offset` 设为 0.02，仅对楼梯 type 3 生效；高度基线保持 `clearance_margin = 0.065`、`over_lift_margin = 0.035`，`over_lift_penalty_weight` 从 0.15 略降到 0.12，给后腿留一点实机余量。

该组目标是验证：不新增 reward 函数时，只通过提高后腿 pair 奖励和 target tracking 占比，能否让后腿在已经交替抬腿的基础上真正抬到足够高度。观察重点：后腿轮心是否越过台阶沿、后轮顶住空转是否减少，以及是否引入后腿砸地、俯仰扰动、关节限位或 value loss 尖峰。若 A 组仍无改善，再考虑 B 组新增 rear high target bonus。

## 4. 强后腿 reward B 组配置

在 A 组强后腿 reward 基础上切到 B 组，保留 `load_run = Jun29_21-55-59_`、`max_iterations = 1500`、`progress_weight = 0.55`、`rear_lift_target_offset = 0.02`、`stairs_pair_escape = 1.0`、`rear_pair_weight = 2.5` 等配置。B 组新增 `stairs_rear_target_bonus`，scale 为 0.5。

预期观察：相比 A 组，B 组应更直接提高后腿越过台阶沿的高度。如果 sim2sim 出现后腿砸地、俯仰扰动、关节限位或 value loss 尖峰，则优先降低 `stairs_rear_target_bonus` scale 到 0.25~0.3，或把阈值从 0.7 提高到 0.8。

## 6. Jun30_01-27-21_ 与 Jun30_01-57-31_ sim2real 结果

sim2real 后确认，两个模型仍然存在后腿抬不起来的问题。相对来说，A 组 `Jun30_01-27-21_` 表现更好：在合适速度下，后腿有机会抬起来并通过台阶；但这个速度窗口比较苛刻，稍微偏离后仍会后腿卡住。B 组 `Jun30_01-57-31_` 虽然训练中 `stairs_rear_target_bonus` 生效，但实机没有带来更明显改善，且从训练指标看它的关节限位、冲击、力矩和 value loss 风险更高，因此当前不建议继续沿 B 组高位 bonus 方向加大权重。

这个结果说明，单纯增强后腿 lift reward 或后腿高位 bonus，已经不能稳定解决实机后腿卡住。A 组在合适速度下能抬起来，说明策略并非完全不会抬后腿，而是对进入后腿脱困动作的速度、接触力、机身姿态和轮子抵住台阶沿的位置非常敏感。问题更像是后腿脱困触发条件和速度窗口太窄，而不是缺少一个更高的目标高度。

下一步建议不要继续直接加 `stairs_rear_target_bonus` 或把 `rear_pair_weight` 再放大。更合理的方向是围绕 A 组做鲁棒化：一方面在训练中增加后腿触障时的速度/接触状态覆盖，让策略在不同前进速度、轮子打滑程度、机身俯仰和接触相位下都能进入后腿抬腿；另一方面可以考虑对后腿 pair 卡住时的“低进度 + 后轮触障”加入更直接的脱困触发奖励或惩罚，而不是只奖励抬高本身。

短期可优先以 A 组 `Jun30_01-27-21_` 为基线继续，而不是 B 组。观察和调参重点应变为：后腿能抬起来时的速度范围、卡住时 base 前进速度和轮速空转状态、后轮触障力是否达到阈值、以及机身 pitch 是否影响后腿 lift。若要做下一组 AB，建议一组围绕速度/指令分布鲁棒化，另一组围绕后轮卡住状态的脱困触发，而不是继续堆高位 lift bonus。

## 7. 关于速度/指令分布假设的修正

进一步讨论后认为，“上楼梯速度窗口苛刻”不应简单归因于训练中缺少对应速度指令。当前 blackW 在 difficult terrain 上已经有 y/yaw 指令随机采样，x 方向也通过 low-speed 与 high-velocity env 覆盖了较宽范围；楼梯上实际已经暴露了随机指令。因此下一步不应优先新增楼梯专用 command sampling。

更合理的解释是：后腿能否抬起来取决于实机接触状态和执行器误差，而不是单纯命令速度本身。合适速度只是让后轮触障力、轮子空转、机身 pitch、后腿 lift timer 和齿轮虚位状态刚好进入可脱困区域；速度稍偏离后，后腿虽然有抬腿意图，但触发/执行不足，仍会被台阶沿卡住。

后续 AB 应改为：A 组加强实机虚位/执行器误差建模，让策略学会在更差的 calf backlash、腿部电机强度和阻尼条件下仍给出足够后腿动作；B 组新增后轮卡住状态的脱困触发 reward，只在后轮触障、前进不足或空转明显时推后腿脱困。两组都不再以新增 command sampling 为主要变量。

## 8. 实机虚位鲁棒化 A 组配置

根据速度/指令分布假设的修正，先切到实机虚位鲁棒化 A 组。该组从 `Jun30_01-27-21_` 继续训练 2000 iter，保留强后腿 reward 基线：`progress_weight = 0.55`、`rear_lift_target_offset = 0.02`、`stairs_pair_escape = 1.0`、`rear_pair_weight = 2.5`。关闭上一轮 B 组的 `stairs_rear_target_bonus`，scale 设为 0.0，不再继续堆高位后腿奖励。

本组只加强执行器/虚位随机化：`calf_backlash_range` 从 `[0.005, 0.035]` 扩到 `[0.01, 0.055]`，`calf_backlash_min_kp_scale` 从 0.12 降到 0.08，`hip_motor_strength_range` 从 `[0.8, 1.05]` 扩到 `[0.75, 1.05]`。目标是让策略在更差的后腿小腿虚位、自由行程 Kp 衰减和髋部输出条件下，仍学会给出足够后腿脱困动作。

预期观察：如果 A 组有效，sim2real 中后腿抬起不应只依赖很窄的速度窗口，轻微偏离合适速度时也能进入后腿脱困；同时需要观察训练侧是否出现关节限位、冲击、torque 或姿态变重。如果 A 组无明显改善，说明仅靠虚位随机化仍不足，需要进入 B 组的“后轮卡住状态触发脱困”reward。

## 9. 后轮卡住触发脱困 B 组配置

在实机虚位鲁棒化 A 组基础上切到 B 组，保留 `load_run = Jun30_01-27-21_`、`max_iterations = 2000`、强后腿 reward 基线，以及加强后的虚位/执行器误差随机化：`calf_backlash_range = [0.01, 0.055]`、`calf_backlash_min_kp_scale = 0.08`、`hip_motor_strength_range = [0.75, 1.05]`。B 组继续关闭 `stairs_rear_target_bonus`，不再堆高位后腿奖励。

该组目标是验证：问题是否来自“后轮卡住状态缺少明确脱困触发”，而不是后腿高度 reward 本身不够。预期 B 组只应在后轮顶住空转且前进不足时更积极抬后腿；如果出现平时后腿乱抬、砸地、俯仰扰动或关节限位变重，应降低 `stairs_rear_stuck_escape` 到 0.4~0.5，或提高 `progress_ratio_threshold`/`slip_speed_threshold` 让触发更保守。

TensorBoard 末 100 iter 看，A 组 `mean_reward` 约 74.75、`terrain_level` 约 5.43、`rew_progress` 约 0.516；B 组分别约 74.42、5.38、0.509，整体没有超过 A 组。B 组新增的 `rew_stairs_rear_stuck_escape` 稳定触发，末 100 约 0.00139，1000 个记录点中 999 个非零，说明该门控并不罕见，但量级偏小。与此同时 B 组 `rew_stairs_pair_escape` 和 `rew_stairs_multi_contact_progress` 略高，说明脱困相关 reward 确实被推了一点。

当前训练侧判断：B 组新增 stuck escape 没有造成明显发散，但也没有在课程等级、progress 或总 reward 上形成明确收益；它更像是一个小量级触发项，可能不足以改变实机后轮卡住策略。后续仍需要 sim2sim/sim2real 判断后腿是否更容易在卡住时抬起。如果肉眼没有改善，下一步不建议简单继续加权到很大，优先考虑检查 stuck escape 的门控是否过宽导致每步都有小奖励、或将奖励从“后腿高段 lift progress”改成更直接的“卡住后实际 forward progress/轮心越过台阶沿”。

## 11. 回看 Jun02_22-30-50_ 早期丝滑楼梯模型

用户反馈早期 `Jun02_22-30-50_` 刚训练出来的一版上楼梯很丝滑，主要不足是碰到障碍时轮子空转严重，因此考虑回退到该版本路线。检查该 run 后确认：它保存了 `model_4000.pt`，当前 blackW 的观测维度、privileged obs 维度和 action 维度仍与该 run 一致，因此可以直接作为当前代码的续训初值，不需要为了加载模型回退整套代码。

该 run 与当前 Jun30 楼梯专线差异很大。Jun02 的非零 reward 基本只有 tracking/progress/姿态/平滑/静止类：`tracking_lin_vel_x = 1.0`、`tracking_lin_vel_y = 0.75`、`tracking_ang_vel = 0.75`、`progress = 1.0`、`action_rate = -0.08`、`smoothness = -0.015`、`base_height = -10.0`、`orientation = -0.5`、`hip_default = -0.8`、`run_still = -0.05` 等；`wheel_obstacle_lift = 0.0`，后续的 `wheel_obstacle_spin`、`stairs_multi_contact_progress`、`stairs_pair_escape`、`stairs_rear_target_bonus`、`stairs_rear_stuck_escape`、`wheel_lateral_clearance`、`dof_pos_limits`、`foot_impact_vel` 等当时都没有启用。当前 Jun30 则启用了强 lift、pair escape、多轮接触、lateral clearance、限位/冲击约束和更强 tracking/orientation，这些很可能已经把动作从 Jun02 的“贴着滚过去”推向更复杂的抬腿脱困模式。

如果要恢复 Jun02 的动作先验，必要恢复项应优先是：从 `Jun02_22-30-50_` 加载 checkpoint；关闭所有后续复杂越障 reward；把基础 reward scales、entropy/symmetry、terrain proportions 和新增执行器随机化尽量回到 Jun02 附近。完整回退历史代码不建议作为第一步，因为 Jun02 训练指标里存在明显 base_height/value loss 异常，说明旧代码/旧地形高度统计有已知问题；当前更合理的是保留后来的代码修复和日志/课程基础设施，只用配置把 reward 与随机化恢复到早期简单形态。

建议下一组先做两条短线：A 组为“纯 Jun02 行为恢复”，使用 Jun02 checkpoint + Jun02 简单 reward，不启用 lift/spin；B 组在 A 组基础上只加轻量连续 `wheel_obstacle_spin`，用于解决空转问题，先不要恢复 `wheel_obstacle_lift` 或 pair/stuck 类 reward。这样可以区分：丝滑动作是否来自 Jun02 的简单 reward/早期 checkpoint，以及空转能否用局部 anti-spin 单独处理，而不重新引入后续复杂抬腿逻辑。

## 12. Jun30 A 组实机好转与 Jun02/Jun30 双线续训规划

sim2real 新反馈：`Jun30_13-38-24_` 相比之前的楼梯模型有小幅好转，后腿虽然仍会卡一会，但最终能够抬上来并通过；这说明实机虚位/执行器误差鲁棒化 A 组方向有效，且当前后腿问题不再是完全无法脱困。不过新的副作用是前腿看起来有些被压住，可能与当前楼梯专线中过强的后腿导向有关：`stairs_pair_escape.rear_pair_weight = 2.5`、`front_pair_weight = 0.6`、`rear_lift_target_offset = 0.02`，再叠加多轮协调和 over-lift 约束后，策略更偏向保后腿脱困，前腿 lift credit 和动作自由度相对不足。

同时回看 `Jun02_22-30-50_`：该早期模型的上楼梯动作更像“贴着滚过去”的先验，但姿态稳定性不足，且当时 `wheel_obstacle_lift = 0.0`，后续的 anti-spin、pair escape、限位/冲击约束、轮胎摩擦/虚位随机化都没有完整接入。因此不建议直接把 Jun30 的整套强后腿 reward 搬到 Jun02，否则很可能破坏其丝滑滚越动作；更适合只补少量稳定性与空转约束，先验证早期动作先验能否保留。

下一组建议双线并行：

1. Jun30 线从 `Jun30_13-38-24_` 继续，目标是保留“后腿最终能抬上来”的收益，同时缓解前腿被压住。优先不要启用 `stairs_rear_stuck_escape`，而是小幅提高前腿 pair 信号、降低后腿相对主导性，例如将 `front_pair_weight` 从 0.6 提到 0.8~0.9，`rear_pair_weight` 从 2.5 降到 2.0~2.2；`rear_lift_target_offset` 暂保留 0.02，若后腿仍够用再考虑降到 0.015。`over_lift_penalty_weight` 可从 0.12 小降到 0.10，给前腿一点余量，但不建议直接全局提高 `clearance_margin`，避免重新出现砸地和关节限位。

2. Jun02 线从 `Jun02_22-30-50_` 继续，目标是保留贴障滚动动作先验，只补稳定和空转。建议使用楼梯专线地形比例，但第一轮不要打开强 lift / pair escape / rear offset；可只加入轻量连续 `wheel_obstacle_spin` 和 `stairs_multi_contact_progress`，再补 `dof_pos_limits`、`foot_impact_vel`、适中的 `run_still`、轮胎摩擦或轻量虚位随机化。该线重点观察是否仍能保持低幅滚越、是否空转减少、姿态是否比原 Jun02 稳定。如果 Jun02 线加少量约束后仍姿态差，再逐步引入更强姿态项，而不是马上加入 Jun30 的强后腿 reward。

## 13. 从 Jun30_13-38-24_ 继续的 pair escape 增强 A 组配置

根据实机反馈，暂不启动 `Jun02_22-30-50_` 早期路线，继续从 `Jun30_13-38-24_` 分叉。本轮目标是同时提高前腿和后腿的楼梯脱困能力，其中后腿仍然加得更多；前腿不是主要问题，但也需要随同增强，避免只强化后腿导致前轮触阶后动作余量不足。

A 组只增强 `stairs_pair_escape` 这一条相对干净的脱困信号：`stairs_pair_escape` scale 从 1.0 提到 1.5，`front_pair_weight` 从 0.6 提到 0.7，`rear_pair_weight` 从 2.5 提到 2.8。`progress_weight = 0.55`、`rear_lift_target_offset = 0.02`、`over_lift_penalty_weight = 0.12` 保持不变；`stairs_rear_target_bonus = 0.0`、`stairs_rear_stuck_escape = 0.0`，不再使用上一轮 B 组的卡住触发项。runner 设置为从 `Jun30_13-38-24_` 续训 1000 iter。

该组验证的是：在现有后腿已经能最终抬上的基础上，单纯放大 pair 内至少一个轮子完成 lift progress 的奖励，能否减少前/后轮抵台阶沿后的等待和空转。观察重点是后腿卡住时间是否缩短、前腿是否保持或略有增强、`rew_stairs_pair_escape` 是否明显上升，以及 `dof_pos_limits`、`foot_impact_vel`、`torques` 是否因更强抬腿驱动而变重。

## 14. 从 Jun30_13-38-24_ 继续的 target 到达增强 B 组配置

在 A 组之后切到 B 组，仍从 `Jun30_13-38-24_` 续训 1000 iter，并继续关闭 `stairs_rear_target_bonus` 与 `stairs_rear_stuck_escape`。B 组不再主要放大 pair escape 总强度，而是验证“前后腿到达 lift target 的倾向和后腿实机高度余量是否不足”。

关键配置：`stairs_pair_escape` 从 A 组的 1.5 降为 1.2，`front_pair_weight = 0.7`、`rear_pair_weight = 2.8` 保持；`progress_weight` 从 0.55 降到 0.50，让 `wheel_obstacle_lift` 中 target reward 占比提高；`rear_lift_target_offset` 从 0.02 提到 0.025，只对楼梯 type 3 后腿生效；`over_lift_penalty_weight` 从 0.12 降到 0.10，给前后腿抬到目标留一点余量。

该组比 A 组更激进，预期后腿越台阶沿的高度余量更足，前腿也会因 target 占比提高和 over-lift 放松而稍有释放。风险是动作幅度、砸地、`dof_pos_limits`、`foot_impact_vel` 和力矩可能变重。对照时重点看：如果 A 组只缩短卡住时间但后腿高度仍不足，而 B 组明显更容易过沿，则说明目标到达/高度余量是主因；如果 B 组只是动作更大但实机无改善，应回到 A 组或折中 `progress_weight = 0.525`、`rear_lift_target_offset = 0.02~0.022`。

## 15. Jun30_17-09-17_ 与 Jun30_17-11-25_ 训练对照

`Jun30_17-09-17_` 是 pair escape 增强 A 组，`Jun30_17-11-25_` 是 target 到达增强 B 组。两组都从 `Jun30_13-38-24_` 续训 1000 iter 到 `model_40000.pt`，共同关闭 `stairs_rear_target_bonus` 与 `stairs_rear_stuck_escape`，并保持 `front_pair_weight = 0.7`、`rear_pair_weight = 2.8`。A 组使用 `stairs_pair_escape = 1.5`、`progress_weight = 0.55`、`rear_lift_target_offset = 0.02`、`over_lift_penalty_weight = 0.12`；B 组使用 `stairs_pair_escape = 1.2`、`progress_weight = 0.50`、`rear_lift_target_offset = 0.025`、`over_lift_penalty_weight = 0.10`。
